# pay_calendar:C13-b as built

How `pay_calendar:C13-b` came to be built on 2026-09-03, at `e2c325dc`. Cite it
for the argument, never as a plan of record.

## What shipped

Finding **P75**'s nineteen hand-written ownership comparisons, retired. Ruling
**R-PC46** (developer, 2026-09-03) split them into two questions that `C13-a`'s
composite key answers only one of:

- **ELEVEN walked `X.pay_period.user_id`** on a row that EXISTS, and became one
  equality on `X.user_id`, exact by `fk_transactions_owner_period`. The SEVEN
  stamp/scope reads of the same expression moved with them; the plan defers
  those as "a performance question C13-b may take while it is there", and
  leaving them would have kept a hydration for a value the row now carries.
- **EIGHT fetched `budget.pay_periods` by an id a USER SUBMITTED** and compared
  it. Those went to the owner's derived calendar, not to the key: the key
  answers what may be STORED, and deleting the check does not refuse the
  request, it changes the ANSWER. Measured -- `routes/transactions/create.py`
  catches the `IntegrityError` and returns `400 "Invalid reference..."` where
  the security response rule asks for the 404 "not found" gets.

`transactions._helpers._resolve_owned_period` is that lookup given a name, and
`_resolve_grid_cell`'s inline copy (C2-f3e's) now shares it. Finding **N-373**
landed in the same commit: `transaction_service.delete_transaction` reconciles
its `owner_id` against the row, ahead of `deletion_refusal`.

## The measurements, and why each was taken

Three docstrings rested on reasons this step deleted, which is the class
`feedback_a_fix_describes_itself_ungraded` names.

| what | before | after |
|---|---|---|
| `GET /transactions/<id>/cell` | 12 statements, 1 hydration | 12 statements, 1 hydration |
| `resync_all_cash_postings` eager load | 1 hydration | 0 -- the option is DEAD, and deleted |
| `POST /transfers` recurring, 6 rows | 82 statements | 88 (+1 per generated row) |
| `PATCH /transfers/instance/<id>` moving a period | 21 statements | 23 (two payday reads either side) |

The cell's load did not go, it MOVED -- from the ownership walk to
`render_transaction_cell`'s due caption. `_render_helpers`' "costs nothing here"
had claimed the ownership check paid for it.

`C13-a` deferred the `user_id` index question to this step. Re-decided: **still
no index.** All nineteen moved reads are attribute reads on a row already loaded
by primary key; no `WHERE transactions.user_id` was added anywhere.

## What was weighed and REFUSED

- **The period-set SCOPES** in `statement_match._candidates` (two) and
  `reconcile_service._rows`. Two of those carried a comment predicting C13-b
  would move them. It does not: each is also what makes its span lookup TOTAL,
  and `Transaction.user_id` cannot supply that.
- **`reconcile_service._rows`' `joinedload(Transaction.pay_period)`.** Its last
  NAMED consumer went with this step, but the transfer arm's census was never
  taken, so the option stays with a hand-off predicate rather than a count. Its
  twin in `posting_service` WAS deleted, because that query excludes shadows and
  is therefore enumerable -- the asymmetry is the discriminator, not an oversight.
- **Collapsing the second period resolution in `update_transfer`.** One
  statement to recover, against a guard block whose ORDER is load-bearing.

## What the review caught, because it is the honest half

Twelve findings on the diff, then THREE MORE in the fixes:

1. **Two invented citations, written while correcting other people's.**
   `_update._validate_update_references` does not exist; and a sentence claiming
   `_instances` still resolves a period, in a diff that had deleted exactly that.
2. **A `:meth:` citation naming the wrong class** -- and the substitute passed a
   grep, which is how the first one had been caught. Resolved by collection
   (`--collect-only`: 1 vs 0), not by grep.
3. **A transitive-key argument naming the one key that cannot carry it.**
   `fk_transactions_owner_period` is satisfied by construction of the backfill
   (`SET user_id = p.user_id FROM budget.pay_periods p`) and refuses nothing;
   `fk_transactions_owner_account` is what grades it. **Migration
   `d4a92f6b13c8`'s own docstring says so**, which is where it should have been
   read the first time.

Every symbol the final diff cites was then resolved by AST rather than grepped:
71 cited, all 55 real code symbols resolve, 4 `Class.member` pairs, 0 wrong.

## The open thing this step names and does not fix

`transfer_recurrence` calls `create_transfer` once per generated occurrence, and
`_get_owned_period` now derives a calendar each time -- **+1 statement per
generated row**, against the ~13 per row that loop already costs. The caller HAS
the resolved period (`_new_row` is handed a `DerivedPeriod` and passes only its
id); the fix is to thread it through `TransferSpec`, which is 84 construction
sites. Recorded in `_get_owned_period`'s docstring with the number.
