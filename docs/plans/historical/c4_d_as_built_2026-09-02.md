# pay_calendar:C4-d as built (2026-09-02)

Archived out of `implementation_plan_pay_calendar.md` on the developer's ruling that an
as-built is unnecessary where it survives in the committed code. Shipped at
**`327a70f2`** (step `65dd6902` + the id renumber), merged in the c4-d PR.

- [x] **C4-d -- the cadence type stops admitting a row that cannot exist.** `327a70f2`. Ruling
      **R-PC45**. `ScheduleFacts` copied two columns off one `budget.pay_schedule` row and typed
      both optional, while the columns are `NOT NULL` (`cadence_days`) and nullable
      (`history_opens_on`) -- so a pair naming no cadence beside a stated opening was constructible
      in Python and unrepresentable in the database, **the defect `C4-b-2` removed from the SCHEMA
      surviving one tier up in the TYPE**. `resolve_schedule` returns an OPTIONAL `ScheduleFacts`
      whose `cadence_days` is a plain `int`.
      **The fork R-PC44 deferred to this leaf was ruled REFUSE**: `calendar_for` keeps its
      `-> PayCalendar` signature and raises `PayCalendarError` for an owner with no schedule row,
      which is what `cadence_for` has done since `R7a-2a` and which `app/error_handlers.py` already
      answers. **No call site changed** -- and the honest re-measurement is 40 in `app/`, not the 48
      R-PC44 quoted.
      **What it DELETED**, which is the leaf's whole point: six `int | None` declarations
      (`ScheduleFacts`, `PayCalendar` and its `from_paydays`, `derive_periods`, and three producers
      in `_views`), the twenty-line "paydays with no cadence" refusal, `PayCalendar.cadence`'s own
      raise -- that property is TOTAL now -- five prose preconditions including `_views`' concession
      that it *"cannot check for itself"*, and the two live `cadence_days is not None` guards in
      `balance_at/_inputs.py` and `investment_dashboard_service/_context.py`. The two refusal
      messages `calendar_for` and `cadence_for` would each have carried are ONE, in
      `_loader._require_schedule`.
      **It SHIPPED WITH A REGRESSION and only a TRAVERSING test found it.** The refusal made
      `settings._load_pay_periods_context` raise, `pay_periods.generate_form` redirects there, and
      `errors/no_pay_calendar.html` offers exactly that link -- so the recovery page's own repair
      answered the recovery page. Two adversarial reviews examined the same claim: the one that
      asserted the link was RENDERED passed it, the one that FOLLOWED it found the loop. The fix is
      the root cause rather than a guard -- **the page that CREATES a schedule is a soft-door caller
      by definition** -- and it collapsed a redundant per-render schedule read while it was there
      (that section called `calendar_for` AND `get_schedule` for one row: the **P68** / **P69**
      class).
      **What it COST, stated**: `/grid` and the account cash-detail page answer
      `errors/no_pay_calendar.html` instead of their own blank render for a row-less owner. Nothing
      live moves -- `register_user` writes the row AND real paydays since `balance:X-ad-a`, no door
      in `app/` deletes one, and the only row-less user is the companion. **The decorator is NOT
      what protects the loader**, which an AST census of all 224 routes corrected:
      `routes/companion`, `routes/entries` and `transactions.mark_done` build calendars under
      `@login_required` alone, and what keeps the companion out is that each resolves the owner from
      DATA. A new companion-reachable surface spelling `calendar_for(current_user.id)` would 500.
      **What a later step must obey**: an EMPTY calendar is still ordinary and now carries a REAL
      cadence -- a schedule row with zero paydays, which `reset_pay_periods` passes through -- so a
      case wanting one takes `bare_user_with_cadence`, never `bare_user`. Opened **P81**, **P82**.
