{# Shared recurrence-rule form fields (Recurring cluster Loop B, P4). Single source for the recurrence picker that templates/form.html (recurring income / expense) and transfers/form.html (recurring transfer) previously each defined verbatim. The two forms differ only in two parameters, so the markup itself is shared here and the differences are passed in: * include_due_day -- only transaction templates carry a separate bill due-day; the transfer schemas do not expose the field. * the pay-period selector's placement -- a transaction's start period only matters for a recurring pattern (it sits INSIDE #recurrence-fields, hidden with the container in the manual case), while a transfer needs it for the one-time case too (it sits OUTSIDE the container). So start_period_field is a separate macro each form places itself; it is not baked into recurrence_detail_fields. An include_none_option flag used to be a third: the transfer form had no "does not repeat" option, because a one-time transfer carried a ONCE RULE. Plan step R2e-3 retired that pattern -- a definition that does not repeat has no rule on either kind -- so both forms now offer the empty option and the flag went with the divergence it described. The REC_* pattern-id Jinja globals LEFT at plan step R7b-2, with the pattern . ``picker`` is the PickerModel the route resolved from app.services.recurrence.picker_model. Its ``options`` are the readings the closed pattern set can actually STORE -- derived from the encoder's own table, not from the pattern enum -- so a cadence encode_cadence would refuse is never offered, and that refusal is unreachable through this form rather than fenced behind it (developer ruling 2026-08-12). ``options_json`` is the same set for recurrence_form.js, which LINKS the three: the unit decides which intervals may show, and the (unit, interval) pair decides which placements may. That pair dependency is real -- the closed set stores "every 1 month funded from the first paycheck" and has no quarterly twin -- so a placement list keyed on the unit alone would offer the unstorable. ``selected`` is the SelectedCadence the edit routes resolved through edit_form_cadence, or None on a create form AND for a rule whose stored pattern the application no longer models. The second case renders the controls unset above a flashed explanation: there is no pattern id left to preserve as a trailing option, so there is nothing for the browser to silently replace with the first entry -- the destructive "Does not repeat". The empty unit option is what "does not repeat" is on both kinds since plan step R2e-3: it posts an empty value, which the create routes read as "author no rule" and the update routes read as "delete the rule this template had" (plan step R2e-1). Both interval controls post ``interval_n``, so exactly one is ever enabled; a disabled control does not submit, which is what keeps two spellings of one field from reaching the schema together.
