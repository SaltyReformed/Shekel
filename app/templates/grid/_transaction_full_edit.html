{# Settled on -- the civil day the money actually moved (ruling R-ED). Rendered ONLY for a row that is currently settled, because that is exactly when the fact exists: a Projected row's money has not moved, so there is no day to state. Deliberately NOT disabled on a finalised row, unlike the money / period / due-date fields above: those are BUDGET DECISIONS the lock protects from being rewritten, and this is an OBSERVED FACT about the bank, which gets corrected when the statement disagrees (``_helpers._LOCKED_EDIT_FIELDS`` carries the rule). Changing it MOVES MONEY on the grid -- since plan step E1a this day is the ``entry_date`` the row's ledger postings are filed under, and the route reconciles them to the new day in the same request. An empty submit means "leave the day alone", not "clear it": the schema field is not ``allow_none``, so ``strip_empty_strings`` DROPS an empty value. A settled row always carries a day; the way to remove one is to set Status to Projected, which clears it at the seam -- and the ``title`` says so, because a comment here is read by nobody who needs it. ``max`` is TODAY (ruling R-EJ): a settled row's money has already moved, so the day cannot be one that has not happened. The browser refuses first and ``status_seam.reject_future_settle_day`` is the backstop, the same layering accounts/form.html uses for an anchor's observed_on. There is deliberately no ``min`` -- a settle legitimately falls before its own pay period (11 of 156 settled rows on the 2026-08-03 production clone do). #} {% if txn.status and txn.status.is_settled %}
